## [CISA 敦促立即修复已被利用的 Ivanti Connect Secure 零日漏洞](https://www.cisa.gov/news-events/alerts/2026/10/13/cisa-urges-patching-newly-exploited-vulnerability-ivanti-connect-secure) ⭐️ 9.0/10

## [GitLab 修复严重未认证远程代码执行漏洞 CVE-2026-97229](https://www.rapid7.com/blog/post/etr-cve-2026-97229-critical-unauthenticated-remote-code-execution-in-gitlab) ⭐️ 9.0/10

2026 年 10 月 12 日，GitLab 发布了针对 CVE-2026-97229 的关键补丁，该漏洞是 CI/CD 正则表达式编译器中的整数溢出（CWE-190），CVSSv3.1 评分为 10.0，影响社区版和企业版。Rapid7 在未修补的官方 GitLab CE 镜像上独立复现了任意代码执行，证实该漏洞可被利用。 由于该漏洞可通过网络访问、评级为最高严重级别，并允许在 GitLab 应用工作进程中执行代码，任何允许公开项目或自助注册的自管理实例都面临直接风险。Rapid7 建议受影响实例在正常补丁周期之外紧急升级，因为利用该漏洞仅需恶意 CI/CD 配置和精心构造的 UTF-8 仓库路径。 利用该漏洞需要攻击者将恶意的 .gitlab-ci.yml 文件以及包含 UTF-8 字符的仓库路径提交到公开项目的分支；在允许新用户自助注册并创建项目的实例上，这一前提条件可轻易满足。精心构造的正则表达式以 US-ASCII 形式通过 GitLab 的校验，但 Ruby 的 Onigmo 引擎在校验完成后会针对 UTF-8 重新编译它，从而触发整数溢出并生成无效指令，使攻击者能以 git 用户身份执行操作系统命令。

rss · Rapid7 Emergent Threat Response · Oct 13, 11:29

**背景**: GitLab 是一个广泛使用的 DevOps 平台，其 CI/CD 流水线在规则条件、变量匹配和作业控制逻辑中支持正则表达式，这些模式在流水线运行前会被编译。CWE-190（整数溢出或回绕）发生在算术计算超出变量可表示范围时，会产生意外值并可能破坏程序状态。GitLab.com 已完成修补，GitLab Dedicated 客户无需采取行动，但所有类型的自管理部署仍受影响。

## [Rust 借用检查器被发现存在 11 年之久的健全性漏洞](https://github.com/rust-lang/rust/issues/164250) ⭐️ 8.0/10

GitHub 议题 #164250 报告了 Rust 借用检查器中一个可追溯约 11 年之久的健全性漏洞，编译器会接受违反 Rust 生命周期规则的代码。该议题在 Hacker News 上引发广泛讨论（669 分、373 条评论），涉及编译器正确性以及 Rust 长期存在的健全性缺陷积压问题。 Rust 的核心价值在于其类型系统所保证的内存安全，因此借用检查器中的健全性漏洞——即便容易修复——也会削弱人们对编译器正确性的信心。这一发现还凸显了 100 多个未解决的健全性缺陷积压问题，并引发了对实际 crate 是否受影响的疑问。 根据社区分析，该漏洞并非 Rust 类型系统本身的缺陷，而是编译器实现层面的错误：借用检查器本应依据现有生命周期规则拒绝这段代码，因此修复方式是让编译器拒绝该代码，而非修改语言的生命周期规则。该议题只是当前 100 多个被标记为 unsound 的问题之一，新的 trait solver 可能会为其中一些问题的修复扫清障碍，但很可能不包括这一个。

hackernews · formerly_proven · Oct 13, 10:27 · [社区讨论](https://news.ycombinator.com/item?id=50069499)

**背景**: Rust 的借用检查器是编译器的一部分，负责执行所有权和生命周期规则，确保引用不会比其指向的数据存活更久，从而在编译期防止数据竞争和释放后使用等错误。所谓“健全性”（soundness）漏洞，是指编译器接受了本应被拒绝的程序，可能导致本应安全的代码出现未定义行为。Rust 长期存在此类问题的积压，社区会区分类型系统规则本身的缺陷与编译器实现这些规则时的缺陷。

## [CERT/CC 指出主流 TLS 库对 X.509 名称约束处理不一致](https://kb.cert.org/vuls/id/573195) ⭐️ 8.0/10

CERT/CC 发布了漏洞公告 VU#573195，记录了 Go、OpenSSL、Apple、LibreSSL、pyca/cryptography、wolfSSL 和 GnuTLS 在 X.509 名称约束处理上的不一致，涉及 DNS 名称比较、IP 地址处理、URI 授权解析和通配符匹配。公告引用了 CVE-2026-3833（GnuTLS 大小写敏感问题，已在 3.8.13 修复）和 CVE-2026-34073（pyca/cryptography，已在 46.0.6 修复），CERT/CC 正在与受影响项目协调。 由于不同 TLS 库可能接受或拒绝同一张证书，混合的 service mesh、CDN 或企业 PKI 环境可能出现验证结果不一致，从而可能导致证书验证绕过或互操作失败。该问题影响广泛部署的库，并凸显 RFC 5280 对若干名称约束行为规定不足。 差异涵盖 DNS 名称大小写不敏感匹配（GnuTLS CVE-2026-3833）、IPv4 与 IPv4 映射 IPv6 的处理、URI 授权解析中 userinfo、冒号、查询或片段出现时的行为（OpenSSL 已合并 PR #30319 处理路径/查询/片段中的 '@'），以及 RFC 5280 未定义的通配符 SAN 语义（LibreSSL、wolfSSL 和 pyca/cryptography CVE-2026-34073）。利用需要攻击者拥有对所选证书字段的可信签名、可达的受影响验证路径，以及使用所接受身份进行授权的应用。

rss · CERT CC Vulnerability Notes · Oct 13, 18:27

**背景**: X.509 名称约束是 RFC 5280 定义的一种证书扩展，允许 CA 限制其可签发证书的命名空间，例如将某 CA 限制在 host.example.com 及其子域。TLS 库实现该扩展以判断证书链对给定名称是否有效，但 RFC 5280 并未完全规定如何比较 DNS 名称、处理 IP 地址、解析 URI 授权或解释通配符。当各库出现分歧时，一个库接受的证书可能被另一个库拒绝，因此 CERT/CC 正在协调跨库审查。
